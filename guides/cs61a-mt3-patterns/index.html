The one move behind every problem

Before writing any code, answer one question: what do I carry down the recursion? Almost every MT3 problem is "process a structure, one piece at a time, while remembering something as you go." That something is the state you thread through the recursive call. Name it first and the code writes itself.

What the state turned out to be, across the problems you drilled:

  • A remaining budget that shrinks (longest: n - s.first; only_paths: n - t.label).
  • A running total you accumulate (prefix sums; the (total, cur) pair in close).
  • Two positions into two sequences (drip: i, j, plus the expected value k).
  • Nothing extra at all, when the structure itself carries the state (most tree and list recursions).

The universal skeleton for any recursion:

def f(structure, carried_state):
    if base_case(structure):      # smallest input: empty list, leaf, 0
        return base_answer        # [], 0, True, None, the element itself
    # combine THIS piece with the recursive answer on the REST
    return combine(this_piece, f(rest, updated_state))

Three checks before you trust a recursion: (1) the base case returns the right type, (2) every recursive call moves strictly toward the base case, (3) you actually use the recursive result rather than recomputing it. If you can state the subproblem in one English sentence ("the best I can do from here with budget k"), you have it.

Recursion & tree recursion

Tell: "count the ways," "is it possible to reach n," "longest/best subset," any problem where each element is independently in or out. Tree recursion means two or more recursive calls per step.

Move: the with/without branch

For each element, either use it or skip it, and recurse on the rest.

def count_ways(s, n):
    if n == 0:
        return 1          # hit the target exactly: one valid way
    if n < 0 or not s:
        return 0          # overshot, or ran out of elements
    use  = count_ways(s[1:], n - s[0])   # take s[0]
    skip = count_ways(s[1:], n)          # leave s[0]
    return use + skip

Swap the combine step for the flavor of question:

  • Count ways to hit a target (Aim for 100, Parking, ways): return use + skip.
  • Does any subset work (A Perfect Question, semiperfect): return use or skip with True/False base cases.
  • Best/longest subset (Best of Both, longest): return max(use, skip, key=...) or the provided longer(use, skip).
  • Collect all subset results (Doctor Change): return sorted(set(skip + [s[0] + x for x in skip])).

Traps that passed weak tests but were wrong: Almost a Perfect Question used d % n == 0 instead of n % d == 0 (the setup line killed a correct recursion). In close, trying to collapse the tail to one number and multiply breaks precedence; carry (total, cur) and fold into cur, never the whole tail.

Pitfall: put the n < 0 (overshoot) and not s (empty) checks before any s[0] access, or you index an empty list.

Lists & dicts

Tell: work with indices, slices, build a result list, count/group items, or compare two sequences position by position.

Index iteration & prefix sums

To include element i, slice to i + 1 because the right end is exclusive (Prefixes (list)).

[sum(s[:i + 1]) for i in range(len(s))]   # prefix sums

Try every position

Loop k over range(len(s) + 1) and collect the hits (all_splice, Seek Once). The + 1 matters when the end position is legal.

return [k for k in range(len(a) + 1) if splice(a, b, k) == c]

Two-pointer / merge

Walk two sequences with separate indices, advancing whichever front matches what you need (drip). Guard each access with its bound so a finished list just forces picks from the other.

k, i, j = s[0], 0, 0
while i < n or j < m:
    if i < n and s[i] == k:
        i += 1; k += 1
    elif j < m and t[j] == k:
        j += 1; k += 1
    else:
        return False
return True

Dict accumulation

Build a dict in one pass (Group By, Lowest): d[key] = d.get(key, default) or check if key not in d first.

Pitfalls: slicing off-by-one (s[:i] excludes s[i]); assuming s and t strictly alternate in a merge (any order within each list is allowed); trusting a green checkmark as proof (symmetrical passed a wrong solution against a weak test, so re-read your own logic).

Linked lists

Tell: the input is a Link. You access s.first and s.rest, and the base case is s is Link.empty (which is ()).

Move: recurse on s.rest, build new Links going back up

"Do not mutate" is automatic if you only ever construct new nodes and never assign to an existing .first or .rest.

def keep(s, n):                 # non-mutating rebuild
    if s is Link.empty:
        return s                # return the empty list unchanged
    rest = keep(s.rest, n)      # solve the rest first
    if should_keep(s.first, n):
        return Link(s.first, rest)   # new node in front
    return rest                 # drop s.first, splice past it

Thread a budget when there is a running constraint

Pass n - s.first into the rest, and use the provided combiner to pick the better branch (How Long is this Exam? / longest).

def longest(s, n):
    if s is Link.empty:
        return s
    skip = longest(s.rest, n)
    if s.first <= n:
        take = Link(s.first, longest(s.rest, n - s.first))
        return longer(take, skip)
    return skip

Pitfalls: the base case is s is Link.empty, not s.rest is Link.empty (checking .rest skips the last node or crashes on empty); build Link(s.first, recursive_call), never s.rest = ...; the reduced budget goes only into the take branch, while skip keeps n.

Trees

Tell: the input is a Tree with t.label and t.branches (a list of Trees). is_leaf(t) is not t.branches. The recursion almost always loops over t.branches.

Move A: aggregate a value

Combine this label with the recursive results from every branch (Sum Labels, Count Leaves, Tree Height, Max Path Sum).

def tree_sum(t):
    return t.label + sum(tree_sum(b) for b in t.branches)

def height(t):
    if is_leaf(t):
        return 0
    return 1 + max(height(b) for b in t.branches)

Move B: build a new tree

Recurse on branches, wrap results in a fresh Tree, never mutate t (Double Every Label).

def double(t):
    return Tree(t.label * 2, [double(b) for b in t.branches])

Move C: prune to valid paths

Carry a remaining budget, keep a node only if a qualifying path runs through it (Only Paths).

def only_paths(t, n):
    if is_leaf(t):
        return Tree(t.label) if t.label == n else None
    kept = [only_paths(b, n - t.label) for b in t.branches]
    kept = [b for b in kept if b is not None]
    return Tree(t.label, kept) if kept else None

Pitfalls: a leaf has height 0 and holds a value, so handle it before max(...) over empty branches; for prune problems keep a node if any branch survives (filter out None first); pass n - t.label to branches, not n.

Mutation & iterators

Tell: the problem says to change a list in place (Insert After), build/update a dict, or pull values from an iterator with next.

In-place list mutation

Inserting or deleting while iterating by index shifts everything after it. Walk backwards, or use a while loop with your own index and step past what you inserted.

def insert_after(s, x, y):      # insert y after every x, in place
    i = 0
    while i < len(s):
        if s[i] == x:
            s.insert(i + 1, y)
            i += 2              # step over x AND the new y
        else:
            i += 1

Why a plain for i in range(len(s)) fails: range(len(s)) freezes the length, and i += 1 inside a for does nothing (the loop reassigns i each pass), so you reprocess the inserted element and fall out of sync.

Consuming an iterator

next(it) pulls one value and advances; it is gone after. next(it, default) avoids StopIteration at the end (Take From Iterator).

def take(it, n):
    return [next(it) for _ in range(n)]   # first n values

Pitfalls: an iterator is one-directional and consumed (no indexing, no re-looping); mutating methods (.append, .insert, .pop) return None, so never s = s.append(x); dict iteration is insertion order, which matters when the output must be ordered.

Generators

Tell: the problem says "yield," "generator," or "lazily produce." A function with any yield in it returns a generator; calling it runs no code until you iterate.

Move: yield one value; yield from relays a whole sub-generator

yield from gen is shorthand for for x in gen: yield x.

def evens(s):
    for x in s:
        if x % 2 == 0:
            yield x            # emit, then pause here until asked again

Recursive generator

Recurse with yield from, then yield the current piece. The order of the two lines sets output order (Prefixes, Tree Labels Generator).

def prefixes(s):
    if len(s) == 0:
        yield s                # the single empty prefix
    else:
        yield from prefixes(s[:-1])   # all shorter prefixes FIRST
        yield s                       # then the whole thing

def tree_labels(t):
    yield t.label
    for b in t.branches:
        yield from tree_labels(b)     # relay each branch's labels

Pitfalls: in prefixes, yield from must come before yield s for shortest-to-longest (flip them and you get longest-first); yield from gen relays values while yield gen emits the generator object itself; a generator runs nothing until iterated and uses yield, not return, for output.

OOP

Tell: define a class, model state with instance attributes, or subclass with super().

Move: __init__ sets state; methods read and update self

class Account:
    def __init__(self, name):
        self.name = name
        self.balance = 0
    def deposit(self, amount):
        self.balance += amount
        return self.balance
    def withdraw(self, amount):
        if self.balance >= amount:
            self.balance -= amount
            return self.balance
        return 'Insufficient funds'

Inheritance

Subclass reuses the parent through super(), which already binds self, so you pass only the real arguments (Checking Account).

class CheckingAccount(Account):
    fee = 1
    def withdraw(self, amount):
        return super().withdraw(amount + self.fee)   # no self passed

Memoization

A closure holds a private cache; check before computing (Memoize).

def memo(f):
    cache = {}                 # lives across calls via the closure
    def memoized(x):
        if x not in cache:
            cache[x] = f(x)
        return cache[x]
    return memoized

Pitfalls: super().method(args) takes no self (super().__init__(self, name) passes it twice and raises TypeError); a state-changing method must actually assign to self (the Vending Machine bug returned the message but never decremented stock or spent the balance); compute dynamic messages instead of hardcoding; the memo cache must live in the outer function, not inside memoized, or it resets every call.

Exam-day checklist

Read these right before you walk in.

  1. Name the carried state first. Budget, running total, two pointers, or nothing. Write it down before any code.
  2. Base case returns the right type. Empty list returns [] or (), a count returns 0, a search returns None/False, a tree returns a Tree or None.
  3. Every recursive call shrinks the input. s[1:], s.rest, t.branches, n - something. If nothing shrinks, it loops forever.
  4. Check bounds before indexing. if i < len(s) and if s guard every s[i] and s[0].
  5. Do not mutate when told not to. Build new Link(...) / Tree(...) nodes; never assign to an existing .rest or .branches.
  6. super().m(args) takes no self. And a state-changing method must actually assign to self.
  7. yield from before yield self for shortest-first order; a generator uses yield, not return.
  8. Trace one small case by hand before moving on. Passing the given doctest is not proof; weak tests hide real bugs.

Time discipline: about 2.5 minutes per point. Start with the WWPD/tracing question for fast points, then your strongest data-structure topic, recursion in the middle, weakest last. If any part runs past ~1.5x its budget, write your best partial and move on. Partial credit across all five questions beats a perfect answer on three.
