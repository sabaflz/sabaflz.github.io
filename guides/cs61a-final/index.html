New unit

Gleam: the language

Gleam is a statically typed functional language with C-style syntax. Three things make it feel different from Python: values are immutable, there are no loops (you recurse), and you branch by pattern matching with case instead of long if-chains.

Functions, let, and anonymous functions

Functions use fn (add pub to make one public). The last expression is the return value, with no return keyword. Types are annotated with : Type.

pub fn add(a: Int, b: Int) -> Int {
  a + b        // last expression is returned
}

let name = "Gleam"      // immutable binding
let x = 5
let x = x + 1           // rebinding (shadowing) is allowed; x is now 6

let double = fn(n) { n * 2 }   // anonymous function
double(5)                       // 10

The pipe operator

|> feeds the value on its left in as the first argument of the call on its right. It reads top to bottom instead of inside-out.

[1, 2, 3]
|> list.map(fn(x) { x * 2 })   // [2, 4, 6]
|> list.filter(fn(x) { x > 2 }) // [4, 6]

// same as: list.filter(list.map([1,2,3], fn...), fn...)

case: pattern matching

case checks a value against patterns, top to bottom, and runs the first that matches. The compiler forces you to cover every shape, which is why a missing base case is a compile error, not a silent bug.

case n {
  0 -> "zero"
  1 -> "one"
  _ -> "many"        // _ matches anything (the catch-all)
}

Custom types

A type lists its constructors. One constructor with named fields is a record; several bare constructors form an enum you match on.

pub type Shape {
  Circle(Float)
  Rectangle(Float, Float)
}

pub fn area(s: Shape) -> Float {
  case s {
    Circle(r) -> 3.14 *. r *. r
    Rectangle(w, h) -> w *. h
  }
}

Two small gotchas: booleans are capitalized (True, False), and Gleam keeps Int and Float math separate. Int uses + - * /; Float uses +. -. *. /. (with the dot). Mixing them is a type error.

New unit

Gleam: recursion & lists

Lists are the workhorse. A list is [1, 2, 3]; you build a longer one by prepending with the spread operator: [0, ..xs]. You take one apart by pattern matching: [] is empty, [first, ..rest] splits off the head.

let xs: List(Int) = [1, 2, 3]
let ys = [0, ..xs]      // [0, 1, 2, 3]

The standard list recursion

Every list function has the same shape: a case with an empty-list base and a [first, ..rest] recursive step. This is exactly the Link recursion from Python, with first/rest built into the pattern.

pub fn sum(xs: List(Int)) -> Int {
  case xs {
    [] -> 0
    [first, ..rest] -> first + sum(rest)
  }
}

pub fn length(xs: List(a)) -> Int {
  case xs {
    [] -> 0
    [_, ..rest] -> 1 + length(rest)
  }
}

pub fn double_all(xs: List(Int)) -> List(Int) {
  case xs {
    [] -> []
    [first, ..rest] -> [first * 2, ..double_all(rest)]
  }
}

The three library functions to know

From gleam/list: map transforms each element, filter keeps some, fold collapses to one value. Note the list comes first.

list.map([1, 2, 3], fn(x) { x * 2 })            // [2, 4, 6]
list.filter([1, 2, 3], fn(x) { x > 1 })        // [2, 3]
list.fold([1, 2, 3], 0, fn(acc, x) { acc + x }) // 6

fold is the general one: it carries an accumulator (acc) across the list, combining it with each element. map and filter are both special cases of fold.

New unit

Tail calls

A function call is in tail position if it is the very last thing a function does, with no work left to do on its result. When every recursive call is a tail call, the language can reuse one stack frame instead of stacking up a new one per call, so the recursion runs in constant space and never overflows.

Not tail recursive vs. tail recursive

// NOT tail recursive: after sum(rest) returns, we still add first.
pub fn sum(xs: List(Int)) -> Int {
  case xs {
    [] -> 0
    [first, ..rest] -> first + sum(rest)   // the + is pending work
  }
}

// Tail recursive: the recursive call IS the whole answer.
pub fn sum(xs: List(Int)) -> Int {
  sum_acc(xs, 0)
}
fn sum_acc(xs: List(Int), acc: Int) -> Int {
  case xs {
    [] -> acc
    [first, ..rest] -> sum_acc(rest, acc + first)   // nothing pending
  }
}

The trick is the accumulator. Move the pending work (the + first) into an extra parameter that you update before recursing, so the recursive call is the last action. The base case then returns the accumulator instead of a fixed value. Ask of any recursive call: is anything still waiting to happen after it returns? If yes, it is not a tail call.

New unit

Interpreters

An interpreter is a program that runs other programs. It takes source code, turns it into a data structure (parsing), then evaluates that structure. The core is two functions that call each other: eval and apply.

The read, eval, print loop

  1. Read: turn the text of an expression into a data structure (a tree of the expression's parts).
  2. Eval: compute the value of that expression in an environment.
  3. Print: display the result. Then loop.

eval and apply

eval(expression, environment) looks at what kind of expression it is and acts accordingly:

  • A literal (a number) evaluates to itself.
  • A name is looked up in the environment.
  • A call evaluates the operator and the operands, then hands them to apply.
  • A special form (like an if or a definition) has its own rule and does not evaluate all its parts first.

apply(function, arguments) runs a function on already-evaluated arguments: it makes a new environment binding the parameters to the arguments, then evaluates the function body in that environment. That body evaluation calls eval again, which is the mutual recursion at the heart of every interpreter.

Why special forms are special: a normal call evaluates all its operands first. But if must not evaluate both branches, and a definition must not evaluate the name being defined. So special forms are handled by eval directly, before the evaluate-all-operands step. Knowing which forms are special, and why, is a classic exam question.

New unit

SQL (declarative programming)

SQL is declarative: you describe what you want, not how to compute it. A query selects columns from tables, filters rows, groups them, and aggregates.

The shape of a SELECT

SELECT columns
  FROM table
  WHERE condition          -- filter individual rows
  GROUP BY column          -- make groups
  HAVING group_condition   -- filter groups
  ORDER BY column          -- sort
  LIMIT n;                 -- cap the rows

Clause order matters, and the mental order is: FROM picks the rows, WHERE filters them, GROUP BY buckets them, HAVING filters buckets, SELECT chooses the output columns, then ORDER BY and LIMIT.

Aggregation

COUNT(*), SUM(col), MAX, MIN, AVG collapse a group into one number. Use WHERE to filter rows before grouping and HAVING to filter after.

SELECT breed, COUNT(*) FROM dogs
  GROUP BY breed
  HAVING COUNT(*) > 1;     -- only breeds with more than one dog

Joins

Put two tables in the FROM (aliased), and match their rows in the WHERE. A self-join lists a table twice to compare its own rows.

SELECT a.name, b.name
  FROM dogs AS a, dogs AS b
  WHERE a.breed = b.breed AND a.name < b.name;

Recursive queries

A WITH clause defines a temporary table that can refer to itself: a base case UNION a recursive case. This is how SQL does what recursion does in Python.

WITH ints(n) AS (
    SELECT 1
    UNION
    SELECT n + 1 FROM ints WHERE n < 5
  )
SELECT n FROM ints;        -- 1, 2, 3, 4, 5
New unit

Mutable trees

Back in Python. A mutable tree is the same Tree ADT, but now you change it in place by assigning to t.label or t.branches instead of building a new tree. This was out of scope for MT3 but is fair game on the final.

def double_all(t):
    """Double every label in place; returns None."""
    t.label = t.label * 2
    for b in t.branches:
        double_all(b)

def prune(t, x):
    """Remove branches whose label is x, in place."""
    t.branches = [b for b in t.branches if b.label != x]
    for b in t.branches:
        prune(b, x)

Mutating vs. building, the distinction that loses points: a mutating function changes t itself and usually returns None; a building function leaves t alone and returns a new Tree. Read the problem: does it say "in place" or does it say "return a new tree"? Never assign to t.branches in a build problem, and never forget to recurse into the branches in a mutate problem.

Study plan

A plan paces mastery instead of cramming. Your final is Friday, December 18, 11:30am–2:30pm, about five and a half weeks out, so there is time to do this right. The shape, from furthest-out to exam day:

  1. New units first, while there is time to practice them (Gleam, tail calls, interpreters, SQL, mutable trees). These are the least rehearsed, so they carry the most risk and the most upside.
  2. Python review by weakness, using the map above. Deepest on mutation and aliasing, function application, comprehensions, and tree navigation.
  3. Mixed timed practice on past finals, on paper, one full exam in one sitting to rehearse pacing.
  4. Re-solve cold, not re-read. Cover the solution and reproduce it from scratch. Reading creates recognition; writing creates recall, and the exam tests recall.
  5. Taper the last day. Light review of your weak-spot sheet, then rest. A rested brain outscores a crammed one.

Exam-day checklist

  1. Gleam: last expression is the return; cover every case shape; Int math vs Float math (the dotted operators); build lists with [x, ..rest].
  2. Tail calls: ask "is anything pending after the recursive call?" If yes, move it into an accumulator.
  3. Interpreters: eval dispatches on expression type; apply makes a new frame and evals the body; special forms skip the evaluate-all-operands step.
  4. SQL: WHERE filters rows, HAVING filters groups; aggregate with GROUP BY; self-join by listing a table twice.
  5. Mutable trees: "in place" means assign to t.label / t.branches and return None; still recurse into branches.
  6. Python carryover: new list vs same list (= shares, slicing copies); evaluate nested calls inside-out; 0-based indexing; base case returns the right type.
  7. Always: trace one small case by hand before trusting a function. Passing the example is not proving it correct.
